## 1. 背景与需要解决的问题

此前手动测试出现了异常结构化状态（这是历史现象，不代表已确认可在当前代码中复现）：

```json
{
  "date_from": 2025,
  "date_to": 2026,
  "languages": ["[2025", "2026]"]
}
```

期望结果是日期字段保存年份，语言字段仅保存**经过验证的规范语言代码**；如果用户在语言问题中误填 `[2025,2026]`，应返回**可理解的输入错误**，而不能当作语言列表保存。

在所提供的 v0.5.0 代码中，以下逻辑值得重点检查：

- `app/services/clarifier.py` 的 `parse_answer_for_targets()`：`languages` 分支使用 `extract_boundaries(value).get("languages") or split_values(value)`；后者可能把任何逗号分隔的垃圾文本保存为语言。
- `app/schemas/question.py` 中 `ResearchQuestionSpec.languages` 目前是未约束的 `list[str]`，可能缺少数据层兜底校验。
- `app/services/clarifier.py` 中 `apply_field_updates()` 对 `explicitly_unrestricted` 的处理和字段更新需要检查冲突、类型、清空旧值等情况。
- `extract_boundaries()` 和日期解析对多种年份连接符、反向年份及模糊输入的行为需要检查。

**先运行测试确认真实现状；不要直接认定所有问题已复现，也不要根据错误数据擅自更改旧数据库。**

## 3. 任务 P0.1：语言字段的可靠解析与校验

### 3.1 输入与期望输出

以下是至少需要支持的明确表达：

| 用户语言回答 | 规范结果 |
|---|---|
| `中文` | `["zh"]` |
| `英文` | `["en"]` |
| `中英文` | `["zh", "en"]` |
| `中文和英文` | `["zh", "en"]` |
| `英文和中文` | `["en", "zh"]`（或项目既有固定顺序，须稳定、无重复） |
| `中文、英文` | `["zh", "en"]` |
| `zh,en` | `["zh", "en"]` |
| `zh / en` | `["zh", "en"]` |
| `不限` / `不限制` | `languages=[]`，且 `explicitly_unrestricted` 含 `languages` |

如项目已有合法的其他语言代码（如 `ja`、`fr`、`de`），应保留合理扩展能力，不可无理由把系统锁死在中英文；可采用简洁、明确的白名单/规范化规则。不要因为字符串看起来像两个字母就默许任意未知值；优先使用当前依赖实现，无需为此引入庞大的语言库。

### 3.2 严格禁止的结果

下面输入出现在**语言问题**里时必须被拒绝，不能污染 `languages`：

```text
[2025,2026]
2025,2026
2025-2026
abc,def（无法被识别为合法语言时）
[]（纯文本空列表不能默认为“不限”）
```

错误需指出“当前问题需要填写语言，例如：中文和英文；不限请回答‘不限’”，或同等清晰文案。

### 3.3 数据层兜底

- `ResearchQuestionSpec` 应确保新写入的 `languages` 均为合法规范值，不能只依赖聊天解析器。
- 显式 `field_updates={"languages": ["zh", "en"]}` 应合法；`["2025", "2026"]` 必须被拒绝。
- 语言去重、顺序策略应确定且可测试；不得将年份、空白字符串、混合无效项落库。
- 考虑 `StructuredLLMQuestionAnalyzer` 的结构化结果也经过相同模型校验，不能被 LLM 输出绕过。
- 历史库已有污染记录时**不得静默修改**；请考虑严格校验对旧数据读取的兼容风险。如出现旧数据读取失败，报告受影响场景与安全的显式修复建议；本任务不做未经批准的数据迁移。

## 4. 任务 P0.2：年份范围解析和校验

### 4.1 正确解析

至少覆盖：

| 输入 | `date_from` | `date_to` |
|---|---:|---:|
| `2020-2026` | 2020 | 2026 |
| `2020—2026` | 2020 | 2026 |
| `2020 至 2026` | 2020 | 2026 |
| `2020年到2026年` | 2020 | 2026 |
| `2020年以来` | 2020 | `null`，结束年份标记为不限 |
| `截至2026年` | `null`，起始年份标记为不限 | 2026 |
| `不限` | `null`，标记为不限 | `null`，标记为不限 |

### 4.2 错误和边界

- `2026-2020` 不得被 `min/max` 悄悄变成 `2020-2026`；应该提示起止年份顺序错误。注意保持对无顺序语义的双年份表述兼容。
- `2025,2026,2027` 这种超过两个候选年份且无法明确确定范围的输入，应拒绝或明确要求重填，不要猜测。
- `2025-abc`、完全无年份、超出 `ResearchQuestionSpec` 已有边界（1500～2100）的年份均需要合理处理；不应写入脏状态。
- 回答日期问题，不得意外修改 `languages`、`study_types` 等无关字段。
- 初始研究问题文本中的年份识别与多轮澄清问答的年份识别，保持一致的核心规则，避免两套互相冲突的算法。

## 5. 任务 P0.3：`field_updates` 与“不限”的状态一致性

### 5.1 字段更新规则

- 只能更新 `FieldName` 允许的字段及明确支持的 `explicitly_unrestricted`；未知字段必须报错。
- 保持 `MessageRequest` 和 `ConfirmQuestionRequest` 的现有 JSON API 结构，不新增破坏兼容性的必填字段。
- `field_updates` 必须验证值类型、合法性和字段间一致性；不能容忍伪造的无效列表。
- 用户修改某个具体字段时，应该清除该字段旧的“不限”标记。
- 用户把某字段明确改为“不限”时，应确保**实际值与“不限”标记不冲突**：日期为 `null`，列表字段为空列表，其他字段按现有 schema 的合理空值表示。
- `explicitly_unrestricted` 仅接受已知字段名组成的列表，拒绝错误类型、未知字段和与同次显式值更新直接冲突的请求。
- 不能因修订一个字段就覆盖其他已回答字段。
- 无效输入不能部分写入项目状态、澄清轮次或对话历史，成功修正后应可继续原流程。

### 5.2 特别注意 LangGraph

检查 `app/graph/workflow.py` 的 `merge_answer → apply_field_updates` 与 `apply_revision` 路径，确认异常不会产生“轮次已前进但字段没有更新”“API 失败但消息已写入”等状态不一致。仅修复实际复现的问题，不重写整个图。

保留：

- 最多 6 轮澄清；
- `clarifying → awaiting_confirmation → confirmed` 的现有确认流程；
- `interrupt / Command(resume=...)` 和 checkpoint 恢复能力；
- 用户显式确认才能进入阶段 B 的前置条件。
